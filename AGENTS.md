# Project Overview

**Courier SuperApps** — a mobile-first courier management system with customer management, session tracking, route planning, and earnings monitoring. Built with Next.js 16 + Drizzle ORM + PostgreSQL (Supabase).

**Primary audience:** Indonesian couriers/logistics. Indonesian (id) locale is the primary target; English (en) is the fallback.

**Design language:** Google Material Design 3 (MD3) Expressive — large border radii, glassmorphism, spring-based animations, and tactile micro-interactions (`active:scale-90` on all touchable elements). 

**Roadmap** at `ROADMAP.md`. Current milestone: v1.x (foundation & polish). Next major update: v2.0 (The Desktop Era).

## App Purpose (DO NOT OVERRIDE)

This app serves as a **courier's personal logistics toolkit** — a supplement to the company's main app.

### The Problem This App Solves
1. **Company's main app is limited** — couriers can only see waybill number, WhatsApp number, and often-wrong customer-provided addresses
2. **Company deletes delivery history after 1–2 weeks** — couriers lose their records
3. **Couriers previously saved customer data in WhatsApp** — house pictures, locations, and addresses were stored in chat messages, which slowed devices as the database grew and risked accidental data loss

### App's Core Purpose
- 🏠 **Help couriers find customers' home locations** (accurate GPS pins, real addresses, house pictures, landmark notes)
- 💾 **Replace WhatsApp as the customer database** (structured storage of customer info — no more scrolling through chat history)
- 📋 **Preserve delivery history** (company app deletes after 1–2 weeks; this app keeps it permanently)
- 💰 **Track courier performance & earnings** (session progress, delivery stats, salary tracking)

### What This App Is NOT
- **Not connected to the company's database** — all data is entered manually
- **Not a barcode/waybill scanner tool** — scanning was experimental, no plans to use it (no company DB integration)
- **Not a replacement for the company app** — it's a companion tool for the courier's own records

### Feature Rationale
- **Customers** — accurate home locations + house pictures + real addresses (replaces WhatsApp storage)
- **Clusters** — categorizing customers based on their geographic location
- **Session Progress** — track courier performance and preserve delivery history beyond the company's 1–2 week retention
- **Earnings** — track courier salary based on delivery performance
- **Visit Tracking** — record when couriers visit customers (for performance metrics and customer history)
- **Share** — share customer info with customers themselves for confirmation/updates

# Database Schema (`lib/schema.ts`)

All tables use `varchar(7)` primary keys generated by nanoid (custom alphabet excluding similar chars: `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz`). Relations are defined via Drizzle's `relations()` API.

| Table | Notes |
|---|---|
| `users` | `name`, `email` (unique), `password` (bcrypt hashed), `role` (default `"courier"`) |
| `passwordResetTokens` | `email`, `token` (unique), `expires` |
| `customers` | `name`, `phoneNumber`, `address`, `latitude`/`longitude` (text!), `housePictureUrl`, `notes`. M2M with clusters via `customerClusters` |
| `deliveries` | `waybillNumber` (unique), `customerId` (FK cascade), `status` (default `"Pending"`), `codAmount` (text!), `receiverName`, `proofOfDeliveryUrl` |
| `clusters` | `name`, `notes`. M2M with customers via `customerClusters` |
| `logs` | Activity audit trail: `userId`, `userName`, `action`, `details`, `targetId` |
| `errorLogs` | Error tracking: `errorName`, `errorMessage`, `stackTrace`, `pathname` |
| `accessLogs` | HTTP access log: `pathname`, `method`, `ipAddress`, `userAgent` |

**CRITICAL**: `latitude`/`longitude` and `codAmount` are stored as `text`, not numeric types. ID generation uses `lib/utils.ts` -> `generateId()` (nanoid 7-char).

Middleware is defined in `proxy.ts` (NOT `middleware.ts`). Uses `withAuth` from `next-auth/middleware`.

- `/admin/*` routes require `role === "superadmin"`

- Matcher: `"/((?!api|_next/static|_next/image|favicon.ico).*)"`

# Authentication

**NextAuth v4** with **CredentialsProvider** (no OAuth). JWT session strategy.

**Login fields**: `usernameOrEmail` + `password`. Auth via bcrypt compare against `users` table.

**Session user shape** (extended via callbacks):
```ts
{ id: string, name: string, email: string, role: "courier" | "superadmin" }
```

**API route auth pattern**: Use `getToken` from `next-auth/jwt`:
```ts
import { getToken } from "next-auth/jwt";
const token = await getToken({ req, secret: process.env.NEXTAUTH_SECRET });
```

**Two auth tiers in API routes:**
- **Hard auth** (returns 401/403): `/api/search/global`, all `/api/admin/*` routes
- **Soft auth** (token optional, used for logging only): resource CRUD routes (customers, deliveries, clusters, settings, upload)

**Password reset flow**: Forgot password → generates `crypto.randomBytes(32)` token with 1hr expiry → stores in `passwordResetTokens` → **returns token in API response for dev auto-redirect** (no email sending configured).

# API Route Conventions

All routes in `app/api/*/route.ts`. Follow this pattern:

```ts
export async function METHOD(req: NextRequest) {
  try {
    // 1. Optionally extract token: const token = await getToken({ req, secret: process.env.NEXTAUTH_SECRET })
    // 2. Parse body: const body = await req.json()
    // 3. Validate inputs inline (no zod)
    // 4. Execute DB operation
    // 5. Optionally log access: await logServerAccess(req, token)
    // 6. Optionally log activity: await logActivity(...)
    // 7. Return NextResponse.json(...)
  } catch (error) {
    return NextResponse.json({ message: "..." }, { status: 500 });
  }
}
```

**Response conventions:**
- Collections wrapped: `{ customers: [...] }`, `{ deliveries: [...] }`, `{ clusters: [...] }`
- Single resources returned directly (unwrapped)
- Errors: mostly `{ message }`, some use `{ error }` (inconsistency)
- Status codes: 200 (OK), 201 (created), 400 (validation), 404 (not found), 409 (conflict), 403 (forbidden), 500 (server error)
- Dynamic route params: always await: `const resolvedParams = await params; const id = resolvedParams.id`

**Bulk operations**: `/api/customers/bulk`, `/api/deliveries/bulk` accept arrays. Admin bulk delete routes under `/api/admin/*/bulk-delete` use `inArray` with Drizzle.

**File upload** (`/api/upload`): Multipart form via `req.formData()`. Saves to `public/static/uploaded_images/{house_image|proof-of-deliveries}/`. Returns `{ url }`.

**Google Maps URL resolver** (`/api/resolve-maps`): Follows redirects and parses coordinates from multiple URL patterns.

# Logger (`lib/logger.ts`)

Three functions writing to dedicated tables:
- `logActivity(userId, userName, action, details?, targetId?)` → `logs` table
- `logError(userId?, userName?, errorName?, errorMessage?, stackTrace?, pathname?)` → `errorLogs`
- `logAccess(userId?, userName?, pathname, method, ipAddress?, userAgent?)` → `accessLogs`
- `logServerAccess(req, token?)` — convenience wrapper for access logging from API routes

All logs silently swallow errors. Write routes log both access + activity.

# Component Architecture

**All components are `"use client"`** and live in `components/`. Pages can be either server or client components.

**Provider hierarchy** (`app/providers.tsx`):
```
SessionProvider → LanguageProvider → ThemeProvider → ToastProvider → ConfirmationProvider → ErrorBoundary
```

**Provider-provided hooks:**
- `useLanguage()` → `{ t(key), locale, setLocale }`
- `useTheme()` → `{ theme, toggleTheme(), setTheme(theme), setStyle(style) }` — theme/style switches use a simple crossfade (View Transitions API); no circular reveal animation
- `useToast()` → `{ showToast(msg, type?) }` — types: `success | error | info | warning`
- `useConfirmation()` → `{ askConfirmation({ title, message, confirmText?, cancelText?, type? }) }` — returns Promise<boolean>

**Styling conventions:**
- CSS variables for theme colors: `bg-card`, `bg-background`, `text-primary`, `text-secondary`, `border-card-border`, `bg-surface-hover`
- Defined via Tailwind v4 `@theme inline` in `globals.css`
- Dark mode via `.dark` class + `dark:` prefix on every component
- Font sizes use explicit pixel values: `text-[15px]`, `text-[13px]`, `text-[11px]`, etc.
- All interactive elements use `active:scale-90` for tactile feedback
- Button classes defined in globals.css: `btn-primary`, `btn-secondary`, `btn-outline`, `btn-danger`
- Glassmorphism: `bg-card/80 backdrop-blur-xl`
- Input styling: `inputClass` constant defined locally per component (same pattern copied everywhere)

**Framer Motion patterns:**
- Spring config: `{ type: "spring", stiffness: 400, damping: 25 }` (common)
- `AnimatePresence` for modals, toasts, dropdowns
- `layoutId="nav-indicator"` for shared layout animation in BottomNav
- `motion.div` with `whileTap={{ scale: 0.92 }}` for micro-interactions
- Page transitions in `app/template.tsx`: `{ opacity: 0, y: 15 }` → `{ opacity: 1, y: 0 }`

**Modal patterns:**
- Simple: `{isOpen && (<div className="fixed inset-0 z-50 ...">)}` with backdrop click to close + scroll lock via `document.body.style.overflow`
- AnimatePresence-based: used in ConfirmationProvider, AdminWipeData

**Suspense boundaries** are used in pages that call `useSearchParams()` (Next.js requirement):
- `/deliveries/page.tsx`, `/deliveries/new/page.tsx`, `/customers/page.tsx`, `/clusters/page.tsx`, `/reset-password/page.tsx`

# Page Layout Patterns

**Root layout** (`app/layout.tsx`):
```tsx
<Providers>
  <Header />
  {children}
  <BottomNav />
</Providers>
```

**Two page layout patterns:**

1. **Standard scroll** (customers, clusters, deliveries detail, settings):
   ```tsx
   <div className="min-h-screen bg-background pb-24">
     <Breadcrumbs />
     <main className="mx-auto max-w-3xl p-4 sm:p-6">...</main>
   </div>
   ```

2. **Full-height fixed header** (map, admin pages) — inner scroll container:
   ```tsx
   <div className="flex flex-col h-[100dvh] bg-background overflow-hidden">
     <div className="shrink-0 z-30 bg-background">
       <Breadcrumbs />
     </div>
     <main className="flex-1 overflow-y-auto custom-scrollbar pb-32">...</main>
   </div>
   ```

IMPORTANT: Pattern 2 breaks `window.scrollY`-based auto-hide in BottomNav because it uses an inner scroll container. See BottomNav.tsx — it listens to `window.scroll` and checks `window.scrollY`. Pages using Pattern 2 will not trigger auto-hide.

# Design Quirks & Known Issues

1. **BottomNav auto-hide** does NOT work on pages using inner scroll containers (Pattern 2 above). To fix, switch to body-level scroll or refactor BottomNav to use IntersectionObserver.
2. **coordinate fields** (`latitude`/`longitude`) and `codAmount` are `text` type in DB — may need casting when doing numeric operations.
3. **PUT vs PATCH semantics reversed**: `/api/deliveries/[id]` has PUT as partial update and PATCH as full overwrite.
4. **Error response inconsistency**: Some routes use `{ message }`, others use `{ error }` for error responses.
5. **No input validation library** (no zod, no joi) — validation is done inline.
6. **No unit tests or integration tests** visible anywhere in the codebase.
7. **Forgot-password** returns token in API response body (dev shortcut — remove for production).
8. **Admin sub-pages** for clusters, customers, and deliveries show placeholder content ("under construction").
9. **Soft auth on resource endpoints**: POST/PUT/DELETE on customers, deliveries, clusters proceed even without a valid token (auth check is middleware-only for page routes).
10. **No rate limiting or CSRF protection** implemented.
11. **Severe network performance issue**: Fetching lists of customers, deliveries, or clusters takes ~50s with network spikes exceeding 3.5MB/s. Suspected causes: Supabase connection overhead, no pagination/limit on list queries, or excessive relational includes (e.g., `with: { clusters: { with: { cluster: true } } }` loading N+1 for every row). **Fix later**: add server-side pagination + limit, lazy-load relations, and investigate Supabase pool config. **Workaround for slow connections**: implement optimistic local creation (create record in IndexedDB/local state first, sync to server in background) and add loading skeletons with timeout fallback UI.
12. **Transparent Android status bar not possible today**: `<meta name="theme-color">` / manifest `theme_color` transparency is ignored by Chrome Android — MDN says the alpha component is dropped, and `rgba(0,0,0,0)` falls back to **black**. Chrome 135+ edge-to-edge only extends content under the *bottom* gesture bar ("chin"); content behind the *top* status bar is still an in-progress Chrome feature ("short-edges cutout mode", not yet released). Current behavior: `ThemeProvider.syncStatusBar()` matches the bar color to `--status-bar` (tracks light/dark x md3/clay/neu via the View Transitions crossfade), with `viewport.themeColor` and manifest `theme_color` defaulting to `#f4f6fb`. Keep that approach; revisit if Chrome ships short-edges support. Note `viewport-fit=cover` + `env(safe-area-inset-*)` only unlocks the bottom bar on Android today (app already uses `pb-safe` on BottomNav).

# Drizzle ORM Usage Patterns

Three query styles used interchangeably:

1. **Relational query API**: `db.query.customers.findMany({ with: { clusters: { with: { cluster: true } } } })`
2. **Raw SQL**: `sql<number>\`count(...)\`` — used for aggregates (cluster customer counts)
3. **Standard query builder**: `db.select()`, `db.insert().values()`, `db.update().set()`, `db.delete().where()`

`db` is exported from `lib/db.ts`: `drizzle(client, { schema })` where schema is the full `./schema` module.

# Testing Policy

**Every new function or module must include corresponding unit tests.** Tests live in `lib/__tests__/` (or alongside the file as `*.test.ts`). Pure functions (no DB, no network) should be tested first since they require no mocking. Follow existing test patterns in `lib/__tests__/`.

- **Validation schemas**: Test all Zod schemas with valid inputs, invalid inputs, and edge cases
- **Business logic** (e.g. earnings cutoff): Test boundary conditions, month/year transitions, all branches
- **Utility functions** (e.g. cache, utils): Test round-trips, TTL, uniqueness, edge cases
- **Existing tests must not break**: Run `npm test` before committing

# Versioning Policy

**Version bumps are delegated to the agent and happen at commit time.** Whenever the user asks to commit (e.g. "commit", "commit this", "commit and push"), the agent must **bump the version in `package.json` FIRST, then commit**. The version lives in `package.json` (`version` field) and is surfaced to the app via `lib/version.ts` → `APP_VERSION`.

- **Major bump** (e.g. `1.5.0` → `2.0.0`) when the changes are significant: breaking/architectural shifts, new major features, or large-scale refactors.
- **Minor bump** (e.g. `1.5.0` → `1.6.0`) for small-to-medium feature additions or notable polish.
- **Patch bump** (e.g. `1.5.0` → `1.5.1`) for small fixes and tweaks.
- When in doubt, prefer a **minor** bump over no bump.
- Do NOT bump the version when writing changes during a session — bump only as part of the commit step, alongside the commit.
- Record the bump in the **Session Change Log** at the bottom of this file, alongside the change it accompanies.
